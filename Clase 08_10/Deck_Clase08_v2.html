Lo esencial

Los 3 conceptos que no pueden quedar ambiguos

  1. ViewModel = dueño del estado de la pantalla.
    Sobrevive a la rotación porque no está atado al ciclo de vida de la Activity.
  2. StateFlow = flujo observable con un valor actual.
    La View no pregunta "¿cómo está el estado?": se suscribe y reacciona cuando cambia.
  3. La View no decide nada.
    Solo dibuja el estado que recibe y emite eventos hacia arriba. Toda la lógica vive en el ViewModel.

Si al final de la clase puedes explicar estos tres con tus propias palabras, la clase cumplió su objetivo.

Bloque 1 · MVVM

Por qué el ViewModel sobrevive a la rotación

ComponenteVive durante
ComposableMientras está en pantalla
ActivityHasta que se destruye (rotación incluida)
ViewModelHasta que la pantalla se cierra definitivamente

El ViewModel está atado al ciclo de vida de la pantalla, no al de la Activity. Por eso sobrevive a la rotación: la Activity se recrea, pero el ViewModel se reutiliza.

Cuando el usuario sale de la pantalla de verdad, el ViewModel se destruye y su viewModelScope se cancela.

El ViewModel

class ProductosViewModel(
    private val repository: ProductoRepository
) : ViewModel() {

    private val _productos = MutableStateFlow<List<Producto>>(emptyList())
    val productos: StateFlow<List<Producto>> = _productos.asStateFlow()

    private val _cargando = MutableStateFlow(false)
    val cargando: StateFlow<Boolean> = _cargando.asStateFlow()

    fun cargar() {
        viewModelScope.launch {
            _cargando.value = true
            _productos.value = repository.obtenerProductos()
            _cargando.value = false
        }
    }
}

El patrón del estado privado

private val _productos = MutableStateFlow<List<Producto>>(emptyList())
val productos: StateFlow<List<Producto>> = _productos.asStateFlow()
  • _productos es privado y mutable: solo el ViewModel lo modifica
  • productos es público y de solo lectura: la View solo observa

Este patrón se repite en todos los ViewModels del curso. Es la forma de garantizar que la UI no pueda corromper el estado.

La View consume el estado

@Composable
fun PantallaProductos(viewModel: ProductosViewModel = viewModel()) {

    val productos by viewModel.productos.collectAsState()
    val cargando by viewModel.cargando.collectAsState()

    if (cargando) {
        CircularProgressIndicator()
    } else {
        LazyColumn {
            items(productos, key = { it.id }) { producto ->
                FilaProducto(producto)
            }
        }
    }
}

collectAsState() convierte el StateFlow en estado de Compose: cuando el flujo emite, la UI se recompone.

Práctico 2

Ejercicio guiado: eventos hacia el ViewModel

class ContadorViewModel : ViewModel() {
    private val _contador = MutableStateFlow(0)
    val contador: StateFlow<Int> = _contador.asStateFlow()

    fun incrementar() { _contador.value++ }
    fun decrementar() { if (_contador.value > 0) _contador.value-- }
    fun reiniciar() { _contador.value = 0 }
}

@Composable
fun PantallaContador(viewModel: ContadorViewModel = viewModel()) {
    val contador by viewModel.contador.collectAsState()

    Column(horizontalAlignment = Alignment.CenterHorizontally) {
        Text("$contador", style = MaterialTheme.typography.displaySmall)
        Row {
            Button(onClick = { viewModel.decrementar() }) { Text("-") }
            Button(onClick = { viewModel.incrementar() }) { Text("+") }
            TextButton(onClick = { viewModel.reiniciar() }) { Text("Reiniciar") }
        }
    }
}

La View no sabe cómo se modifica el contador: solo llama métodos. Toda la regla vive en el ViewModel.

Diagnóstico

El bug de la lista mutable

// MAL: la UI no se actualiza
private val _items = MutableStateFlow(mutableListOf<String>())

fun agregar(item: String) {
    _items.value.add(item)   // muta la lista sin emitir un nuevo valor
}

Síntoma: agregas un elemento y la pantalla no cambia.

Causa: StateFlow compara por referencia. Si mutas la misma lista, el valor "no cambió" y no emite.

// BIEN: se crea una lista nueva
_items.value = _items.value + item
